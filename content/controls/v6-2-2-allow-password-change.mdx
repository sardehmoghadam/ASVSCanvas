## What This Control Means

Users must be able to change their own password through the application. This is a baseline usability and security capability: when a user suspects compromise, they need a way to take ownership of their credential without waiting for an administrator.

## Why This Matters

If users cannot change their password, they cannot respond to a breach, a shared or forgotten credential, or a phishing attempt. A missing change path also drives users toward insecure workarounds (reusing one password forever, or asking an admin to set a known one). Self-service change is a prerequisite for most other password lifecycle controls.

## Main Security Requirement

> Verify that users can change their password.

In practice this means an authenticated, self-service change endpoint the user can reach.

## Common Failure Patterns

- **No change capability** — passwords set once and never mutable by the user.
- **Admin-only changes** — user cannot self-serve, so admin sets a known value.
- **Broken flow** — UI present but the endpoint is disabled or errors.
- **Change without re-auth** — allowing change without confirming the current session or credential.

## Secure Implementation

Provide an authenticated change endpoint that verifies the current password:

```javascript
app.post("/account/password", authenticate, async (req, res) => {
  const user = req.user;
  const ok = await bcrypt.compare(req.body.current, user.passwordHash);
  if (!ok) return res.status(400).json({ error: "Current password incorrect" });
  user.passwordHash = await bcrypt.hash(req.body.next, 12);
  await db.save(user);
  res.json({ changed: true });
});
```

## Key Rules

- Provide a self-service password change path for every user.
- Require the current password (or a fresh factor) before changing.
- Hash and store the new password with an approved algorithm.
- Notify the user of the change (see V6.3.7).
- Apply the same policy as registration (length, blocklists, breach check).

## Checklist for Code Review

- Can every user change their own password?
- Is the change endpoint reachable and functional?
- Is the current password required before the change?
- Is the new password validated and hashed correctly?
- Is the user notified when the password changes?
