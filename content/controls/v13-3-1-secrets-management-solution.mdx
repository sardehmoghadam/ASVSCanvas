## What This Control Means

A dedicated secrets-management solution (a key vault) must be used to create, store, control access to, and destroy backend secrets — passwords, key material, DB/third-party credentials, token keys and seeds, internal secrets, API keys. Secrets must never appear in source code or build artifacts, and L3 requires a hardware-backed store such as an HSM.

## Why This Matters

Hardcoded secrets in repos and CI artifacts leak through cloning, forking, logs, and dependency scans — and once leaked, they're a nightmare to rotate everywhere. A vault centralizes generation, access control, audit, and revocation, so secrets live in one hardened place instead of scattered through codebases and images.

## Main Security Requirement

> Verify that a secrets management solution, such as a key vault, is used to securely create, store, control access to, and destroy backend secrets. These could include passwords, key material, integrations with databases and third-party systems, keys and seeds for time-based tokens, other internal secrets, and API keys. Secrets must not be included in application source code or included in build artifacts. For an L3 application, this must involve a hardware-backed solution such as an HSM.

In practice this means a vault as the single source of secrets, with HSM backing at L3.

## Common Failure Patterns

- **Hardcoded secrets** — keys/passwords in source or config files.
- **Secrets in artifacts** — baked into images or builds.
- **No vault** — secrets stored ad hoc on disk/DB.
- **Vault bypassed** — secrets copied out to env/notes.
- **No destruction** — old secrets never revoked/deleted.

## Secure Implementation

Fetch secrets at runtime from a vault, never hardcode:

```javascript
const { secret } = await vault.read({
  path: "prod/payments/db",
  key: "password",
});

// SDKs that support it should use dynamic secrets with built-in TTL
const dbCreds = await vault.database.generateCredentials({
  role: "payments-ro",
  ttl: "1h",
});
```

## Key Rules

- Use a key vault for create/store/access/destroy of secrets.
- Never place secrets in source code or build artifacts.
- Centralize all backend secrets in the vault.
- Control and audit access per secret.
- Require hardware backing (HSM) for L3.

## Checklist for Code Review

- Are all backend secrets managed in a vault?
- Are secrets absent from source code and artifacts?
- Is vault access controlled and audited?
- Are secrets destroyed/revoked when retired?
- Is hardware backing (HSM) used at L3?
