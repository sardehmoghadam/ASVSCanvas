## What This Control Means

Each protection level must have written requirements covering the full lifecycle of that data: encryption, integrity verification, retention, logging and access controls around logs, database-level protection, privacy-enhancing technologies, and other confidentiality measures.

## Why This Matters

A protection level without written requirements is just a label. Documentation turns classification into enforceable engineering rules — developers can't consistently implement "what encryption? what retention? what gets logged?" if the answers for each level aren't written down. It's also what auditors and privacy regulators ask for first.

## Main Security Requirement

> Verify that all sensitive data protection levels have a documented set of protection requirements. This must include (but not be limited to) requirements related to general encryption, integrity verification, retention, how the data is to be logged, access controls around sensitive data in logs, database-level encryption, privacy and privacy-enhancing technologies to be used, and other confidentiality requirements.

In practice this means a documented per-level protection profile, not a vague policy.

## Common Failure Patterns

- **Generic policy** — "protect data" with no per-level detail.
- **Encryption-only profiles** — integrity/retention/logging omitted.
- **Log access unaddressed** — no rules for sensitive data in logs.
- **PETs missing** — privacy-enhancing measures never specified.

## Secure Implementation

Document a protection profile per level:

```yaml
protection_levels:
  restricted:
    encryption:
      at_rest: AES-256-GCM
      in_transit: TLS 1.3
    integrity_verification: HMAC-SHA256 on write, verified on read
    retention: delete after 90 days, automatic purge
    logging: never log plaintext; tokenized references only
    log_access: role OPS_AUDIT with reason code
    database_encryption: column-level, application-managed keys
    privacy_tech: pseudonymization, data subject extraction
  confidential:
    encryption: { at_rest: AES-256-GCM, in_transit: TLS 1.2+ }
    retention: delete after 2 years
    logging: minimized fields, redacted values
```

## Key Rules

- Document protection requirements per protection level.
- Cover encryption, integrity, retention, logging for each level.
- Define access controls for sensitive data in logs.
- Specify database-level encryption and PETs.
- Publish profiles so implementers can follow them.

## Checklist for Code Review

- Does every protection level have documented requirements?
- Are encryption and integrity rules spelled out per level?
- Is retention defined per level?
- Are logging and log-access rules specified?
- Are database encryption and PETs covered?
