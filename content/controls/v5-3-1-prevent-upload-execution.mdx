## What This Control Means

Files written by untrusted input must never become executable code when fetched over HTTP. If an upload is stored under a web root, an attacker can drop a `shell.php` and then simply browse to its URL. This control requires that anything in a public folder be served as inert content — never interpreted by the server's runtime.

## Why This Matters

This is the classic webshell upload: upload a file into a directory the webserver executes from, request it, and the server runs attacker code. The fix is not just "validate uploads" — it is a storage decision: keep untrusted files out of the executable web path, or configure that path so nothing in it is treated as code.

## Main Security Requirement

> Verify that files uploaded or generated by untrusted input and stored in a public folder, are not executed as server-side program code when accessed directly with an HTTP request.

In practice this means storing uploads outside the document root and serving them via a download handler with a safe `Content-Type`.

## Common Failure Patterns

- **Uploads inside the web root** — files stored where `http://host/files/x.php` can reach them.
- **Executable extensions served** — `.php`, `.jsp`, `.aspx` allowed in the public directory.
- **Mixed-use directory** — user files live alongside application code.
- **No Content-Type forcing** — the server infers a dangerous type/extension on download.

## Secure Implementation

Store uploads outside the document root and stream them back as static content:

```javascript
const STORE = path.join(__dirname, "../../uploads"); // outside web root

app.get("/download/:id", (req, res) => {
  const file = path.join(STORE, req.params.id);
  res.setHeader("Content-Type", "application/octet-stream");
  res.setHeader("X-Content-Type-Options", "nosniff");
  res.setHeader("Content-Disposition", `attachment; filename="file"`);
  res.sendFile(file);
});
```

## Key Rules

- Store uploaded files outside the document root.
- Never place untrusted files in an executable code path.
- Serve uploads through a handler that forces a safe resource type.
- Do not combine user files with application code in the same directory.
- Add `X-Content-Type-Options: nosniff` on all responses.

## Checklist for Code Review

- Are uploads stored outside the web root, or in a non-executable path?
- Is the upload directory unable to be reached by direct URL as code?
- Does the download handler force a static/non-executable Content-Type?
- Are `.php`/`.jsp`/`.aspx` and similar extensions blocked in storage?
- Is `nosniff` set on file-serving responses?
