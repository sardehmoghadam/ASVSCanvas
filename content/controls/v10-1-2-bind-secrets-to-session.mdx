## What This Control Means

The client must reject any authorization-server response (authorization code, ID Token, etc.) that is not the answer to a flow it started in that same user-agent session and transaction. This is enforced by generating unguessable, transaction-specific secrets — PKCE `code_verifier`, `state`, and the OIDC `nonce` — and binding them to the client and the exact session that began the flow.

## Why This Matters

OAuth flows hop across the browser with redirects, leaving openings for response injection, CSRF, and code interception. The `state`, `code_verifier`, and `nonce` are the client's proof that a redirect response belongs to its own request, not an attacker's. Weak, reused, or unbound secrets let a forged or replayed response be accepted as if it were legitimate.

## Main Security Requirement

> Verify that the client only accepts values from the authorization server (such as the authorization code or ID Token) if these values result from an authorization flow that was initiated by the same user agent session and transaction. This requires that client-generated secrets, such as the proof key for code exchange (PKCE) code_verifier, state or OIDC nonce, are not guessable, are specific to the transaction, and are securely bound to both the client and the user agent session in which the transaction was started.

In practice this means per-transaction secrets stored against the session and verified on the redirect.

## Common Failure Patterns

- **Predictable `state`/`nonce`** — short or fixed values an attacker can guess.
- **Secrets not session-bound** — a value accepted without matching the originating session.
- **Reused across transactions** — one value reused, enabling replay.
- **No `nonce`/`state` check** — responses accepted without validating the round-trip.

## Secure Implementation

Generate, store, and verify per-transaction secrets:

```javascript
const crypto = require("crypto");

// Start flow: bind unguessable secrets to this session
function startFlow(req) {
  const state = crypto.randomBytes(32).toString("base64url");
  const codeVerifier = crypto.randomBytes(32).toString("base64url");
  req.session.oauth = { state, codeVerifier };
  const url = authorizeUrl({ state, codeChallenge: challenge(codeVerifier) });
  return url;
}

// Callback: only accept if the state matches the original session
function onCallback(req, res) {
  if (req.query.state !== req.session.oauth.state) return res.status(403).end();
  // ... exchange code_verifier for tokens
}
```

## Key Rules

- Generate `state`, `nonce`, and `code_verifier` with cryptographic randomness.
- Make each secret specific to a single transaction.
- Bind secrets to the client and the originating user-agent session.
- Verify the round-trip value on every redirect before accepting the response.
- Invalidate/reject any response whose binding does not match.

## Checklist for Code Review

- Are `state`/`nonce`/`code_verifier` generated with a CSPRNG?
- Is each secret unique per transaction?
- Are secrets bound to the originating session?
- Is the returned `state` verified before processing the response?
- Are mismatched or missing bindings rejected (fail closed)?
