## What This Control Means

Access to secrets must follow least privilege: each identity may read only the specific secrets it needs for its function, with no broad or blanket access to the secret store.

## Why This Matters

A vault is only as safe as its access policy. If every workload can read every secret, one compromised service exposes the entire credential inventory. Scoping each identity to its own narrow set of secrets keeps any single breach from unlocking the rest of the system.

## Main Security Requirement

> Verify that access to secret assets adheres to the principle of least privilege.

In practice this means per-identity, per-secret ACLs.

## Common Failure Patterns

- **Blanket access** — one token reads all secrets.
- **Broad roles** — "developer" or "admin" scopes everywhere.
- **No per-secret scoping** — a service reads unrelated secrets.
- **Static long-lived read tokens** — no expiry or rotation.

## Secure Implementation

Scope each identity to exactly its secrets:

```hcl
# vault policy: payments service can read only its own secrets
path "secret/data/payments/*" {
  capabilities = ["read"]
}
# no path rule -> default deny for everything else
```

## Key Rules

- Grant each identity only its required secrets.
- Scope policies to specific secret paths.
- Deny access to secrets by default.
- Separate read vs. write/rotate capabilities.
- Review and prune stale access regularly.

## Checklist for Code Review

- Is secret access scoped per identity?
- Do policies reference specific paths, not `secret/*`?
- Is default access denied?
- Are read and write capabilities separated?
- Is stale/unused access revoked?
