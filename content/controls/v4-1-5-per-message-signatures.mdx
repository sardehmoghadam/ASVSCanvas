## What This Control Means

Transport-level protection (TLS) secures a single hop. When a highly sensitive transaction — a payment, a signed order, a legal instruction — passes through multiple systems, TLS alone cannot prove the message was not altered in between hops or in a queue. A per-message digital signature cryptographically binds the content to its origin, independent of the transport.

## Why This Matters

Multi-hop architectures break the end-to-end guarantee of TLS: each intermediary decrypts and re-encrypts, creating gaps where a message can be modified without detection. A per-message signature survives those hops, providing integrity and (with asymmetric keys) non-repudiation — proof of who sent it and that nothing changed since.

## Main Security Requirement

> Verify that per-message digital signatures are used to provide additional assurance on top of transport protections for requests or transactions which are highly sensitive or which traverse a number of systems.

In practice this means signing the serialized payload (with a nonce/timestamp) at the producer and verifying it at every consuming boundary.

## Common Failure Patterns

- **TLS-only assumption** — trusting that hop-by-hop encryption proves end-to-end integrity.
- **Unsigned replay** — a signature without a nonce or timestamp lets an attacker replay the message verbatim.
- **Shared-secret everywhere** — using a symmetric HMAC when non-repudiation is actually required.
- **Signing headers, not the body** — protecting metadata while the payload itself remains modifiable.

## Secure Implementation

Sign the canonical payload with the producer's private key:

```javascript
import { createSign } from "node:crypto";

function signMessage(body) {
  const payload = JSON.stringify({ ...body, nonce: crypto.randomUUID(), ts: Date.now() });
  const signer = createSign("SHA256");
  signer.update(payload);
  signer.end();
  return { payload, signature: signer.sign(PRIVATE_KEY, "base64") };
}
```

Verify at every consuming boundary with the producer's public key:

```javascript
import { createVerify } from "node:crypto";

function verifyMessage({ payload, signature }) {
  const verifier = createVerify("SHA256");
  verifier.update(payload);
  verifier.end();
  if (!verifier.verify(PUBLIC_KEY, signature, "base64")) {
    throw new Error("Signature verification failed");
  }
  return JSON.parse(payload);
}
```

## Key Rules

- Sign the full canonical payload of sensitive, multi-hop messages.
- Include a nonce and timestamp to prevent replay.
- Use asymmetric keys when non-repudiation is required.
- Verify the signature at each trust boundary, not just at the final consumer.
- Never treat hop-by-hop TLS as an end-to-end integrity guarantee.

## Checklist for Code Review

- Which transactions are classified as highly sensitive or multi-hop?
- Do those messages carry a per-message signature over the full body?
- Is there a nonce/timestamp to defeat replay attacks?
- Are signatures verified at every consuming boundary?
- Is asymmetric signing used where non-repudiation is expected?
