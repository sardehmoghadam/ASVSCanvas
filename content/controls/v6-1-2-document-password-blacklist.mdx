## What This Control Means

Beyond the global "common password" list, each organization has its own easy-to-guess vocabulary: the company name, product names, system IDs, project codenames, department and role names. These must be written down so password validation can reject them (and their obvious permutations).

## Why This Matters

`CompanyName2026!` passes length and composition checks but is the first guess any targeted attacker tries. A context-specific blocklist closes the gap that generic lists cannot, because a password tied to your organization is predictable only to people targeting you specifically.

## Main Security Requirement

> Verify that a list of context-specific words is documented in order to prevent their use in passwords. The list could include permutations of organization names, product names, system identifiers, project codenames, department or role names, and similar.

In practice this means a maintained word list plus a permutation-normalization rule.

## Common Failure Patterns

- **No context list** — relying only on the top-N common password list.
- **Exact-match only** — `Admin` rejected but `Adm1n`, `@dmin`, `admin2026` pass.
- **Forgotten sources** — codenames, product names, and system IDs never added.
- **Static list** — never reviewed as the organization ships new products.

## Secure Implementation

Document the terms and normalize before comparison:

```javascript
const CONTEXT_WORDS = [
  "acme", "acmecorp", "invoicer", "portal", "adminportal", "atlantis",
];

function normalize(word) {
  return word.toLowerCase()
    .replace(/[^a-z0-9]/g, "")
    .replace(/0/g, "o").replace(/1/g, "i").replace(/3/g, "e");
}

function isContextWord(candidate) {
  const norm = normalize(candidate);
  return CONTEXT_WORDS.some(w => norm.includes(normalize(w)));
}
```

## Key Rules

- Maintain a documented list of context-specific blocked words.
- Include org name, product names, system IDs, codenames, and role names.
- Reject permutations and character substitutions, not just exact matches.
- Combine with the common-password and breach list checks.
- Review the list when new products/systems ship.

## Checklist for Code Review

- Is there a documented context-specific password blocklist?
- Does it cover organization, product, system, and role names?
- Are permutations (leet-speak, separators) also rejected?
- Is the list reviewed and updated regularly?
- Is the context check applied alongside common/breach checks?
