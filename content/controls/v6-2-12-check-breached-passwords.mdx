## What This Control Means

New passwords — at registration or change — must be checked against a dataset of passwords known to have appeared in breaches. A value present in that dataset is rejected, because it is already in attackers' credential lists before the user even finishes signing up.

## Why This Matters

Credential stuffing uses one breach's passwords against many sites. If a user picks (or reuses) a previously breached password, every site they use it on is instantly at risk. Checking against breached data at the moment of selection — before storage — prevents known-compromised secrets from ever entering your database.

## Main Security Requirement

> Verify that passwords submitted during account registration or password changes are checked against a set of breached passwords.

In practice this means a local breach list or a privacy-preserving remote check (e.g. k-anonymity via Have I Been Pwned).

## Common Failure Patterns

- **No breach check** — only common-password and context checks.
- **Plaintext transmission** — sending the whole password to a third-party API.
- **Check skipped on change** — registration checks but change does not.
- **Stale dataset** — breach list never refreshed.

## Secure Implementation

Use a k-anonymity approach so the full password never leaves the server:

```javascript
import { createHash } from "node:crypto";

async function isBreached(password) {
  const sha1 = createHash("sha1").update(password).digest("hex").toUpperCase();
  const prefix = sha1.slice(0, 5);
  const suffix = sha1.slice(5);
  const hits = await fetch(`https://api.pwnedpasswords.com/range/${prefix}`)
    .then(r => r.text());
  return hits.split(/\r?\n/)
    .some(line => line.split(":")[0] === suffix);
}
```

Alternatively use a locally checked breach set for fully offline validation.

## Key Rules

- Check new passwords against a breach dataset.
- Apply at both registration and password change.
- Prefer k-anonymity or local data over sending plaintext upstream.
- Reject passwords found in the breach set.
- Refresh the dataset on a schedule.

## Checklist for Code Review

- Is a breach-password check performed on new passwords?
- Is it applied at registration *and* change?
- Does the approach avoid sending the plaintext password off server?
- Are breached passwords rejected before hashing/storage?
- Is the breach dataset refreshed regularly?
