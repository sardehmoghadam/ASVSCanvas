## What This Control Means

Secrets must be configured with an expiration and be rotated on the schedule defined in the application documentation — so every secret has a bounded lifetime and a planned replacement.

## Why This Matters

Even protected secrets should be assumed to leak eventually. Expiration and rotation bound the usefulness of any stolen secret: the clock runs out before an attacker can exploit it indefinitely. Tying rotation to documented schedules turns this into an enforced, predictable control rather than an occasional manual chore.

## Main Security Requirement

> Verify that secrets are configured to expire and be rotated based on the application's documentation.

In practice this means TTLs and automated rotation matching the documented cadence.

## Common Failure Patterns

- **No expiry** — secrets live forever.
- **No rotation** — expiry defined but never rotated.
- **Manual rotation** — depends on someone remembering.
- **Drift from docs** — rotation doesn't match the schedule.

## Secure Implementation

Issue secrets with a TTL and automate rotation:

```javascript
// Dynamic secret: auto-expiring, rotated by the vault
const creds = await vault.database.generateCredentials({
  role: "payments-app",
  ttl: "24h",                 // bound each secret's lifetime
});

// Scheduler aligns with the documented rotation calendar
schedule("0 2 * * *", async () => await vault.rotate("prod/signing-key"));
```

## Key Rules

- Give every secret an expiration/TTL.
- Rotate secrets on the documented schedule.
- Automate rotation rather than relying on manual steps.
- Use dynamic/short-lived secrets where possible.
- Reconcile actual rotation against the documented cadence.

## Checklist for Code Review

- Does every secret expire?
- Is rotation automated and scheduled?
- Does rotation match the documented cadence?
- Are dynamic/short-lived secrets used?
- Is drift between docs and reality checked?
