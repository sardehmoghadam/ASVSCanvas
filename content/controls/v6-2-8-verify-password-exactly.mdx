## What This Control Means

The password the system verifies must be exactly the bytes/characters the user submitted. No truncation to a maximum length, no lowercasing, no Unicode normalization that changes the value, no trimming that strips meaningful characters.

## Why This Matters

Any transformation cleaves the user's secret into a smaller, guessable space. Historically, systems truncated passwords to 8 or 16 characters, so `correct horse battery staple` and `correct horse` authenticated identically — the attacker only needed the first 8 characters. Mismatched normalization across platforms can likewise make valid entries fail or collapse distinctions. Verifying exactly as received preserves the full strength the user chose.

## Main Security Requirement

> Verify that the application verifies the user's password exactly as received from the user, without any modifications such as truncation or case transformation.

In practice this means no silent edits between input, storage, and comparison.

## Common Failure Patterns

- **Truncation** — cutting to a legacy maximum before hashing/compare.
- **Case folding** — lowercasing or uppercasing before storage.
- **Whitespace trimming** — stripping leading/trailing spaces that were part of the secret.
- **Aggressive NFC/NFD normalization** — changing Unicode code point sequences.

## Secure Implementation

Reproduce the stored hash using the untouched original value:

```javascript
async function verify(user, submitted) {
  // 'submitted' is the raw string, unmodified, untrimmed, untruncated.
  return bcrypt.compare(submitted, user.passwordHash);
}
```

Only apply a *conservative* normalization that preserves meaning (if any), and never truncate. If a legacy max length was applied, treat it as a defect and re-hash on next login.

## Key Rules

- Verify the password exactly as the user submitted it.
- Never truncate passwords to a maximum length.
- Never case-transform or trim before hashing.
- Avoid code-point normalization that changes the value.
- If legacy truncation exists, plan a re-hash-on-login migration.

## Checklist for Code Review

- Is the raw submitted password passed to the verifier, unmodified?
- Is there any truncation or maximum-length slicing?
- Is case folding or trimming applied anywhere in the path?
- Is Unicode handled consistently without lossy normalization?
- Are legacy truncation behaviors flagged for migration?
